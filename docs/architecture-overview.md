# 跨境电商ERP — 架构设计概览

> **文档定位**：本文档从架构视角阐述跨境电商ERP系统的设计理念、技术选型权衡、领域划分策略及核心架构决策，旨在展示个人在业务架构、技术架构、数据架构与工程架构方面的综合设计能力。

---

## 1. 设计哲学

本系统的架构设计遵循以下核心原则：

### 1.1 领域驱动优先
以跨境电商的14个业务领域为限界上下文，每个领域内部采用严格的四层 DDD 分层（接口层 → 应用层 → 领域层 → 基础设施层），领域层零框架依赖，确保核心业务逻辑的可测试性和独立性。

### 1.2 演进式架构
首期采用**模块化单体**，以18个 Maven 模块组织代码，降低分布式复杂度；后续可按业务维度（如连接器、BI、工作流）渐进式拆分为独立微服务，无需大规模重写。

### 1.3 事件驱动协作
跨域协作不依赖同步 RPC 调用，而是通过领域事件 + Outbox 模式实现最终一致性。这种设计使各域间解耦，也为未来的微服务拆分铺平了道路。

### 1.4 中台抽象
将跨域通用能力抽象为业务中台（14个）和技术中台（11个），避免能力重复建设，提升系统整体的复用性和一致性。

## 3. 领域划分策略

### 3.1 14个限界上下文

跨境电商的业务链条长、环节多，将整个系统划分为14个领域是我在业务建模阶段的核心设计决策。划分依据如下：

| 领域 | 核心职责 | 划分理由 |
|------|---------|---------|
| **IAM** 身份权限 | 认证授权、多租户、10维数据权限 | 横跨所有域的基础设施，独立管理安全策略 |
| **PDM** 产品开发 | SPU/SKU管理、选品分析 | 商品数据是ERP的核心主数据，独立维护生命周期 |
| **SOM** 销售运营 | Listing管理、价格策略、多渠道刊登 | 运营策略频繁变化，与产品主数据解耦 |
| **ADS** 广告投放 | SP/SB/SD广告活动管理、关键词优化 | 广告具有独立的预算/竞价/分析模型 |
| **OMS** 订单管理 | 订单导入、分合单、履约、退款 | 订单是交易的核心载体，状态流转复杂 |
| **SCM** 供应链 | 供应商管理、采购计划、采购执行 | 采购流程涉及多级审批和财务联动 |
| **WMS** 仓储管理 | 库存台账、入库/出库、质检、盘点 | 库存管理有独立的物理位置和状态模型 |
| **FBA** 亚马逊物流 | FBA库存、补货建议、货件管理 | 亚马逊FBA业务与自有仓的逻辑差异大，独立建模 |
| **TMS** 物流运输 | 物流商、轨迹追踪、运费计算 | 物流渠道多（2000+），需要独立的追踪和计费模型 |
| **CRM** 客服售后 | 客户画像、工单管理、邮件营销 | 客服工作流与核心交易分离，独立响应 |
| **FMS** 财务管理 | 成本归集、应收/应付、利润核算 | 财务数据需要严格的准确性和审计追踪 |
| **BI** 商业智能 | KPI指标体系、报表、趋势分析 | 分析型负载与事务型负载分离，便于扩展 |
| **Dashboard** 工作台 | 经营驾驶舱、待办事项聚合 | 作为各域数据的聚合展示入口，不承载业务逻辑 |
| **SYS** 系统设置 | 系统参数、Webhook、业务规则 | 系统的配置层，与运行时业务逻辑解耦 |

### 3.2 层级划分

我将14个域分为三个层级，以便管理依赖关系：

```
核心层（基础能力）
  IAM ──── SYS ──── Dashboard

业务层（交易闭环）
  PDM → SOM → OMS → FMS
    ↓            ↑
  SCM → WMS → TMS

增值层（增强能力）
  ADS ──── CRM ──── FBA ──── BI
```

## 4. 跨域业务闭环

跨境电商最核心的挑战在于**多域流程编排**。以下五个闭环是本系统的核心业务流程：

### 4.1 销售履约闭环
```
OMS(订单导入→审核→付款)
  → WMS(库存预留→拣货→打包→发货)
    → TMS(物流单生成→轨迹追踪)
      → FMS(收入确认→成本核算)
```

### 4.2 采购入库闭环
```
SCM(供应商管理→采购单→审批→收货)
  → WMS(入库质检→良品放行)
    → FMS(采购成本事件自动生成)
```

### 4.3 智能补货闭环
```
OMS(历史销量分析)
  → SCM(补货建议→采购计划→审批→转采购单)
    → WMS(入库完成→库存更新)
```

### 4.4 出库履约闭环
```
OMS(下发履约指令)
  → WMS(释放库存→拣货→打包→称重→发货)
    → TMS(物流单→轨迹追踪→签收确认)
      → FMS(物流成本归集)
```

### 4.5 广告投放与效果闭环
```
ADS(广告活动管理→出价优化)
  → OMS(广告订单标记)
    → BI(广告效果分析→ROI计算)
      → ADS(策略调整)
```

每个闭环都采用了 **Saga 模式** 保证最终一致性，失败环节通过补偿事务回滚，无需强依赖分布式事务。

## 5. 事件驱动架构

### 5.1 架构模式

```
领域服务 → DomainEventPublisher → Outbox表(同库事务)
  → ScheduledPoller → Kafka/RocketMQ
    → 消费者 → 跨域服务/数据同步
```

**设计要点：**
- **Outbox 模式**：事件先写入业务库的 outbox 表（与业务操作同事务），再由定时轮询发送到消息队列，确保事件不丢失
- **拓扑命名规范**：`erp.{domain}.{aggregate}.{event}.v1`，如 `erp.oms.order.paid.v1`
- **双消息栈**：Kafka 用于高吞吐事件流，RocketMQ 事务消息用于强一致场景

### 5.2 跨域事件拓扑

```
erp.oms.order.paid.v1       → WMS(预留库存) → FMS(确认收入)
erp.wms.inbound.completed.v1 → FMS(成本归集) → SCM(销单)
erp.scm.po.approved.v1      → WMS(预入库通知)
erp.tms.delivered.v1        → OMS(完成履约) → FMS(物流成本核算)
erp.pdm.product.activated.v1 → SOM(可售商品同步)
```

## 6. 数据架构

### 6.1 多租户隔离策略

采用 **Schema 级隔离**（PostgreSQL Schema），每个租户拥有独立的数据表空间：

```
platform  ← 平台级公共数据（全局配置）
iam       ← 租户1的认证授权数据
pdm       ← 租户1的产品数据
...
tenant_2.iam  ← 租户2的数据（如果是独立Schema模式）
```

隔离级别选型权衡：

| 方案 | 隔离性 | 维护成本 | 扩展性 | 选择 |
|------|--------|---------|--------|------|
| Database 级 | 最强 | 最高 | 好 | 暂不采用 |
| **Schema 级** | **强** | **中** | **好** | **✅ 采用** |
| Row 级 | 弱 | 低 | 最好 | MyBatis-Plus 插件辅助 |

### 6.2 实时数据管道

```
PostgreSQL(binlog) → Canal → Kafka → Flink
                                          → Elasticsearch (搜索/聚合)
                                          → Redis (缓存预热)
                                          → ClickHouse (OLAP分析)
                                          → PostgreSQL (物化视图)
```

这个 CDC 架构实现了事务数据到分析系统的近实时同步，避免双写带来的一致性问题。

## 7. 安全架构

### 7.1 认证授权链路

```
客户端 → Kong(SSL终结+TLS) → SCG(JWT验签+租户Header注入)
  → 业务服务(@RequirePermission) → PermissionAspect(AOP)
    → 10维DataScope过滤查询结果
```

### 7.2 10维数据权限模型

传统 RBAC 只能控制"能否访问"，无法控制"能看到哪些数据"。本系统设计了10个数据权限维度：

| 维度 | 说明 | 典型场景 |
|------|------|---------|
| tenant | 租户隔离 | 不同租户数据完全隔离 |
| org | 组织范围 | 集团下不同公司 |
| department | 部门范围 | 部门经理只看本部门数据 |
| store | 店铺范围 | 运营只看负责的店铺 |
| marketplace | 市场范围 | 美国站运营只看US数据 |
| channel | 渠道范围 | 只看Amazon或TikTok数据 |
| warehouse | 仓库范围 | 仓库主管只看负责仓库 |
| supplier | 供应商范围 | 采购只看负责的供应商 |
| category | 类目范围 | 类目经理只看管辖类目 |
| data_level | 脱敏级别 | 明细/汇总/脱敏三种粒度 |

## 9. 技术选型权衡

| 决策点 | 选择 | 备选方案 | 理由 |
|--------|------|---------|------|
| 架构形态 | 模块化单体 | 微服务 | 降低初期分布式复杂度，保留拆分能力 |
| ORM | MyBatis-Plus | JPA/Hibernate | 复杂SQL可控，多租户插件成熟 |
| 消息队列 | Kafka + RocketMQ | 单一MQ | Kafka高吞吐 + RocketMQ事务消息 |
| 注册中心 | Nacos | Eureka/Consul | 注册+配置一体化，Alibaba生态 |
| 网关 | Kong + SCG | 单一网关 | Kong处理边缘，SCG处理后端路由 |
| 前端框架 | Next.js 14 | 纯SPA | SSR/SSG兼顾SEO和首屏性能 |
| 数据库 | PostgreSQL | MySQL | Schema隔离、JSONB、CTE支持更好 |

## 10. 工程架构

### 10.1 Maven模块组织

```
cross-border-erp (父POM)
├── erp-common                 # 公共技术模块
├── erp-gateway                # 内部网关
├── erp-domain-xxx (14个)      # 业务领域模块
└── erp-app                    # 启动聚合模块
```

### 10.2 DDD分层规范（每个领域模块）

```
erp-domain-xxx/
├── api/              ← REST控制器、DTO
├── application/      ← 用例编排、事务协调
├── domain/           ← 纯领域模型（零框架依赖）
│   ├── model/        ← 聚合根、实体、值对象
│   ├── service/      ← 领域服务
│   ├── event/        ← 领域事件
│   └── repository/   ← 仓储接口
└── infrastructure/   ← MyBatis、消息发送、外部客户端
```

**核心约束**：`domain/` 层禁止导入任何 Spring/MyBatis 注解，保证核心业务逻辑的纯粹性。

### 10.3 模块依赖规则

```
erp-app → 所有domain → erp-common
erp-gateway → erp-common
domain之间禁止直接依赖，通过应用服务或事件协作
```

## 12. 设计总结

本系统在架构上的核心亮点：

1. **领域驱动的边界划分** — 14个限界上下文覆盖跨境电商全链路，各域内聚度高、耦合度低
2. **演进式架构** — 模块化单体起步，保留微服务拆分能力，降低初期复杂度
3. **事件驱动的跨域协作** — Outbox 模式确保事件不丢失，Saga 模式保证最终一致性
4. **10 维数据权限** — 远超传统 RBAC 的细粒度权限控制，适配跨境电商复杂的组织架构
5. **中台化的能力复用** — 25个业务/技术中台避免重复建设
6. **CDC 实时数据管道** — Canal + Kafka + Flink 实现事务数据到分析系统的近实时同步
7. **DDD 分层纯度** — 领域层零框架依赖，核心业务逻辑可独立测试
8. **全链路业务闭环** — 从选品到财务核算的端到端流程覆盖
