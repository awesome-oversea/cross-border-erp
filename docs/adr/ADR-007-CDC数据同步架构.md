# ADR-007: CDC数据同步架构

日期：2026-05-01
状态：已采纳
决策者：技术负责人

---

## 上下文

跨境电商ERP系统需要实时数据同步能力，支撑以下场景：
- 缓存一致性：数据库变更→Redis缓存同步
- 搜索同步：数据库变更→Elasticsearch索引更新
- 事件发布：数据库变更→Kafka事件（Outbox替代方案）
- 数据分析：数据库变更→ClickHouse分析库同步
- 跨域数据同步：二期微服务化后跨服务数据同步

---

## 决策

采用 **Canal + Kafka + Flink** CDC数据同步架构：
- **Canal**：PostgreSQL变更数据捕获
- **Kafka**：变更事件传输
- **Flink**：实时数据处理和分发

---

## 备选方案

### 方案A：应用层双写

| 优点 | 缺点 |
|---|---|
| 实现简单 | 一致性难保证 |
| 无额外组件 | 代码侵入性强 |
| | 性能开销大 |

### 方案B：Outbox轮询

| 优点 | 缺点 |
|---|---|
| 一致性好 | 延迟较高 |
| 实现简单 | 轮询开销 |
| 一期已采用 | 不适合大规模 |

### 方案C：Canal + Kafka + Flink（采纳）

| 优点 | 缺点 |
|---|---|
| 一致性好（基于WAL） | 运维复杂度高 |
| 延迟低（毫秒级） | 组件多 |
| 对应用无侵入 | 学习成本 |
| 支持多目标同步 | 一期不需要 |

---

## 理由

1. **一期Outbox够用**：模块化单体内部，Outbox轮询延迟可接受
2. **二期Canal启用**：微服务化后需要CDC替代Outbox
3. **多目标同步**：Canal→Kafka→Flink可同时同步到Redis/ES/ClickHouse
4. **缓存一致性**：Canal CDC替代延迟双删，更可靠
5. **渐进式引入**：一期预留Kafka主题，二期启用Canal

---

## 架构

```
PostgreSQL WAL → Canal → Kafka → Flink → Redis/ES/ClickHouse/PG
```

### 数据流

| 源 | Canal | Kafka | Flink | 目标 |
|---|---|---|---|---|
| PG变更 | 捕获变更 | 变更事件 | 处理分发 | Redis缓存更新 |
| PG变更 | 捕获变更 | 变更事件 | 处理分发 | ES索引更新 |
| PG变更 | 捕获变更 | 变更事件 | 处理分发 | ClickHouse分析 |
| PG变更 | 捕获变更 | 变更事件 | 处理分发 | 跨服务PG同步 |

---

## 分阶段实施

| 阶段 | CDC策略 | 适用场景 |
|---|---|---|
| 一期 | Outbox轮询 | 模块化单体内部事件发布 |
| 二期 | Canal + Kafka + Flink | 微服务化后跨服务同步+缓存一致性 |
| 三期 | Canal + Kafka + Flink + Debezium | 完整CDC生态 |

---

## 影响

- 一期无额外运维负担
- 二期需部署Canal+Flink
- Kafka主题需提前规划
- 数据库需开启WAL逻辑复制
