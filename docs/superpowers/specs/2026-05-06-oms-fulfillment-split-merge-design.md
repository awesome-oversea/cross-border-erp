# OMS 履约计划拆包合包设计

## 背景

当前 `OMS` 已具备：

- 渠道订单导入与标准化
- 风控审核
- 履约计划自动生成
- 分仓库存检查与物流推荐

但 `P2-021` 的验收要求是“拆单、合单、有货先发生成正确履约单/包裹；订单金额和数量不丢失”。现有代码只覆盖了自动拆包和部分发货，还缺少显式的手工拆包/合包操作。

## 四色建模

### 粉色原型

- 拆包时间
- 合包时间
- 履约计划更新时间

### 黄色原型

- 订单处理人员
- 仓库执行人员

### 蓝色原型

- 销售订单
- 履约计划
- 履约包裹
- 拆包命令
- 合包命令

### 绿色原型

- 国家
- 仓库
- Seller SKU

## 范围

### 本轮纳入

- 手工拆包：按订单行和数量生成多个履约包裹
- 手工合包：把多个未发货包裹合并为一个包裹
- 拆包/合包后保证数量和金额守恒
- 暴露 `OMS` 入站接口用于手工操作

### 本轮暂不纳入

- 销售订单层真正的母子单拆分
- 多订单合单
- 规则驱动自动合单
- 包裹级仓库和物流重新分配

## 设计决策

### 1. 操作层级落在履约计划而不是销售订单

当前 `SalesOrder` 没有母子单关系，也没有合单归属字段。如果直接做订单级拆合单，会扩大到 `OrderDO/OrderLineDO/DDL/API` 的结构变更。本轮先在 `OrderFulfillmentPlan` 层完成手工拆包/合包，保持订单主数据稳定。

### 2. 手工拆包生成“待分配包裹”

拆包后的包裹默认不携带仓库和承运商，状态统一置为 `WAITING_INVENTORY`，表示包裹结构已经明确，但分仓和物流优选由后续 `P2-022` 处理。

### 3. 合包会清空原有仓配决策

如果多个包裹被合并，新的包裹默认丢弃原包裹的仓库/承运商分配结果，重新回到 `WAITING_INVENTORY`。这样可以避免把来自不同仓库/不同承运商的旧决策错误沿用到新包裹。

### 4. 守恒校验是核心约束

拆包时：

- 每条订单行分配总量必须精确等于原订单数量
- 不允许超分、漏分或负数

合包时：

- 被合并包裹的数量与金额汇总必须等于新包裹

## API

- `POST /oms/api/in/v1/orders/{orderId}/split`
- `POST /oms/api/in/v1/orders/{orderId}/merge-packages`

## 错误处理

- 订单不存在：`ORDER_NOT_FOUND`
- 已发货订单不可拆合：`ORDER_STATUS_INVALID`
- 无当前履约计划时合包：`FULFILLMENT_PLAN_NOT_FOUND`
- 拆包数量不守恒：`ORDER_SPLIT_QUANTITY_MISMATCH`
- 合包包裹数不足：`FULFILLMENT_PACKAGE_MERGE_INVALID`

## 测试策略

- 拆包生成两个包裹且数量金额守恒
- 拆包数量不守恒时报错
- 合包后包裹数减少且数量金额守恒
- 与既有自动履约计划测试组合执行，确认无回归

## 约束

- 不新增依赖
- 不修改销售订单表结构
- 所有路径锁定 D 盘，C 盘零写入，Maven 依赖新增需审批
