# OMS-WMS-SCM-TMS-FMS 最小经营闭环批量补齐设计

## 1. 目标

在现有 14 域最小骨架和可测 API 基线上，优先批量补齐 `OMS → WMS → SCM → TMS → FMS` 业务闭环，使订单履约、库存流转、采购收货、物流发运、成本归集和利润计算形成一条可持久化、可追溯、可测试、可验收的后端主线。

本批次不追求一次覆盖所有增强规则，而是以《跨境电商ERP系统详细设计说明书V11》《跨境电商ERP系统——任务清单》《跨境电商ERP系统——任务清单-验收标准》为准，优先把一期最小经营闭环中最影响业务真实性与验收完整性的部分补齐。

## 2. 批次范围

### 2.1 纳入范围

- OMS
  - 渠道订单接入后的标准订单状态校验
  - 订单审核结果驱动履约计划
  - 拆单/合单/有货先发的最小闭环
  - 发货后平台回传记录
- WMS
  - 可用库存、预占库存、在途库存、冻结库存的最小账务模型
  - 预占、释放、扣减、入库四类关键库存动作
  - 库存事务流水持久化与追溯
- SCM
  - 采购单提交、审批、收货
  - 收货驱动 WMS 入库
  - 采购收货异常的最小校验
- TMS
  - 承运商、运单、轨迹、妥投
  - 发货动作与物流单联动
  - 平台回传前的物流状态约束
- FMS
  - 成本事件统一入账
  - 平台账单导入
  - 订单维度利润计算
  - 成本来源追溯与利润明细查询

### 2.2 暂不纳入范围

- 复杂策略中心、模拟回放、灰度版本管理
- 完整连接器生态与真实外部平台联调
- BI/驾驶舱展示层
- 所有高阶审批编排、复杂异常补偿编排
- 全量 PMS/AI 建议闭环

## 3. 对应任务与验收映射

### 3.1 直接覆盖的任务

- OMS：`P2-019`、`P2-020`、`P2-021`、`P2-022`、`P2-023`
- SCM/WMS：`P2-027`、`P2-028`、`P2-029`、`P2-031`、`P2-032`、`P2-033`
- TMS/FMS：`P2-037`、`P2-038`、`P2-039`、`P2-040`、`P2-041`
- 财务增强最小骨架：`P4-012`、`P4-013`

### 3.2 本批次验收目标

本批次完成后，至少应满足以下可验证结果：

1. 订单进入审核并生成履约计划，履约计划可生成包裹并进入发货流程。
2. 库存动作形成可追溯的事务流水，数量变化与业务动作一致。
3. 采购收货后可驱动库存入库，并形成对应成本来源记录。
4. 运单、轨迹、妥投状态可落库，发货与物流状态链路一致。
5. FMS 可按订单维度聚合成本并计算利润，不再仅按 SKU 粗粒度汇总。
6. 利润结果可追溯到订单、SKU、采购收货、物流与平台费用来源。
7. 主链路具备集成测试证据，覆盖正向流程和关键非法状态校验。

## 4. 现状判断

### 4.1 已有基础

当前仓库已具备以下基础：

- 多模块 Spring Boot 工程、Flyway、MyBatis-Plus、MockMvc 测试基线已可运行。
- OMS/WMS/SCM/TMS/FMS 已有最小 API、服务、DO、Mapper、Migration 和部分测试。
- FMS 已支持平台账单、成本事件、基础利润接口，但利润计算仍偏向 SKU 汇总。
- OMS、SCM、TMS 已存在指向 FMS 或 WMS 的客户端，说明跨域主线已具备延展点。

### 4.2 当前关键缺口

- 订单、库存、采购、物流、财务之间仍存在“能调用但不够闭环”的情况。
- 利润计算未稳定按订单维度归集成本，容易串单。
- 成本事件来源链字段不够充分，难以满足追溯验收。
- 多个域已具备状态对象，但跨域状态联动与异常校验不够完整。
- 财务增强引擎类存在，但持久化、API、测试并未形成可验收闭环。

## 5. 设计原则

1. **沿用现有分域结构**：继续在 `erp-domain-oms`、`erp-domain-wms`、`erp-domain-scm`、`erp-domain-tms`、`erp-domain-fms` 内补齐，不新建平行实现。
2. **先闭环再增强**：优先保证业务主链路真实可跑，再考虑复杂规则和平台化能力。
3. **持久化优先**：本批新增或调整的关键状态、流水、利润结果必须可落库、可查询。
4. **订单维度为主**：财务归集和利润计算以订单维度为主，SKU 为辅助维度。
5. **审计上下文贯穿**：关键写操作保留 `tenantId`、`traceId`、`actorId`、`sourceType`、`sourceId`。
6. **测试驱动补齐**：每条主链路按失败测试 → 最小实现 → 通过测试推进。

## 6. 业务闭环设计

### 6.1 OMS：订单到履约计划

订单接入后保持标准订单实体为主控对象。审核通过的订单才允许进入履约计划；命中风险或利润异常的订单保持待审或阻断状态。履约计划负责描述本次发货的包裹拆分、SKU 数量和目标承运方案。

本批次中，OMS 需要补齐以下能力：

- 订单审核状态与履约计划状态的约束。
- 拆单、合单、有货先发的最小规则集。
- 订单发货后与 TMS 运单建立稳定关联。
- 平台回传日志与重试状态留痕。

### 6.2 WMS：库存台账与事务账

WMS 在本批次中承担库存真实性主控角色。任何来自订单发货、采购收货、库存释放的动作，都必须转化为库存余额变化和库存事务流水。

本批次统一最小动作类型：

- `RESERVE`：订单预占
- `RELEASE`：取消或回退释放
- `OUTBOUND`：发货扣减
- `INBOUND`：采购收货入库

库存余额至少维护：`availableQty`、`reservedQty`、`inboundQty`、`frozenQty`。每次变化都必须写入事务流水，并关联来源单据。

### 6.3 SCM：采购审批与收货入库

SCM 本批次只保证采购主线的最小真实性：采购单可提交、审批、收货，并通过收货动作驱动 WMS 入库。超收、重复收货、非法状态收货必须被拒绝。

收货完成后，SCM 需要同时输出：

- 采购收货业务结果
- 入库所需的最小明细
- 成本来源信息，供 FMS 记录采购相关成本事件

### 6.4 TMS：运单、轨迹与妥投

TMS 本批次作为履约后的物流状态主控。OMS 发货后创建运单；轨迹更新和妥投结果都由 TMS 管理。平台发货回传必须建立在运单创建成功基础上。

本批次最小状态要求：

- 运单创建
- 轨迹更新
- 妥投完成
- 取消/失败校验

### 6.5 FMS：成本事件、平台账单与订单利润

FMS 本批次是业务真实性补齐的核心。所有利润结果必须回到订单维度，而不是仅按 SKU 汇总。

本批次统一成本来源模型：

- 采购收货成本
- 物流成本
- 平台费用
- 其他运营费用（若已有最小入账接口则接入，否则暂缓）

成本事件必须至少关联：

- `tenantId`
- `orderId` 或等价订单来源标识
- `sellerSku`
- `sourceType`
- `sourceId`
- `costType`
- `amount`
- `currency`
- `occurredAt`

利润计算结果至少输出：

- 订单维度收入
- 成本合计
- 费用合计
- 毛利/利润
- 对应的来源摘要

## 7. 跨域数据流

### 7.1 销售履约主线

1. OMS 接入标准订单。
2. OMS 审核订单，合格后生成履约计划和包裹。
3. WMS 根据履约计划执行预占。
4. OMS/TMS 生成运单。
5. 发货确认后，WMS 扣减库存，TMS 更新运单状态。
6. OMS 记录平台发货回传日志。
7. FMS 记录物流与履约相关成本事件。

### 7.2 采购补货主线

1. SCM 创建采购单并审批。
2. SCM 收货。
3. WMS 根据收货明细执行入库。
4. FMS 记录采购收货相关成本事件。

### 7.3 财务利润主线

1. FMS 接收平台账单。
2. FMS 接收采购、物流等来源成本事件。
3. FMS 按订单聚合收入、成本、费用。
4. FMS 持久化利润结果并提供明细查询。

## 8. 状态与约束

### 8.1 OMS 关键约束

- 未审核通过的订单不得生成可执行发货计划。
- 已取消订单不得再次进入发货。
- 已发货订单不得重复创建同一有效平台回传结果。

### 8.2 WMS 关键约束

- 预占不得超过可用库存。
- 扣减不得超过预占库存或允许发货库存。
- 释放不得超过已预占数量。
- 入库不得为负数或重复计入同一收货动作。

### 8.3 SCM 关键约束

- 仅已审批采购单允许收货。
- 收货数量不得超过允许范围。
- 已完成采购单不得重复完成收货。

### 8.4 TMS 关键约束

- 无运单不得记录有效轨迹。
- 已取消运单不得进入妥投。
- 妥投后不得再次进入创建态或运输中态。

### 8.5 FMS 关键约束

- 成本事件缺失订单来源时，不得进入订单利润计算。
- 同一来源事件必须幂等，避免重复记账。
- 利润计算以订单维度为第一归集单位。

## 9. API 与持久化调整方向

### 9.1 API 方向

保留现有路径规范，只补齐必要接口或调整现有接口行为：

- OMS：履约计划、包裹、平台发货回传接口完善
- WMS：预占、释放、扣减、入库接口及查询
- SCM：采购提交、审批、收货接口完善
- TMS：运单创建、轨迹更新、妥投接口完善
- FMS：成本事件入账、平台账单导入、订单利润计算与明细查询

### 9.2 持久化方向

优先复用已存在表和 DO/Mapper；仅在以下场景增补字段或表：

- 成本事件需要补订单级来源字段时
- 利润结果需要补足订单级持久化结构时
- 平台回传日志、履约计划、库存事务账已有结构不足时

原则上不引入新依赖，不大规模重构表模型，只为闭环与验收补足最小字段。

## 10. 测试设计

本批次按测试驱动推进，最少补齐以下测试：

1. OMS → WMS → TMS 发货主线集成测试
2. SCM → WMS 收货入库主线集成测试
3. FMS 平台账单 + 成本事件 + 订单利润计算集成测试
4. 非法状态测试
   - 库存不足预占失败
   - 未审批采购单收货失败
   - 非法物流状态迁移失败
   - 无订单来源成本事件不得进入订单利润计算
5. 订单利润追溯测试
   - 同 SKU 多订单场景下，利润不串单

## 11. 实施顺序

1. 先补测试，明确当前失败点。
2. 先打通 OMS/WMS/TMS 销售履约主线。
3. 再补 SCM/WMS 收货入库主线。
4. 最后补 FMS 成本归集与订单利润计算。
5. 收尾补查询接口和验收证据。

## 12. 风险与取舍

### 12.1 风险

- 现有跨域客户端与服务边界不完全一致，可能需要小幅收敛接口。
- 旧的 `erp-common` 内存式财务/成本引擎与 `erp-domain-fms` 可能存在能力重叠，需避免双轨实现继续扩散。
- 若部分表结构已存在但字段不足，Flyway 增量脚本需要谨慎保持兼容。

### 12.2 取舍

- 本批次优先选择“能验收的真实闭环”，不追求一次做完整规则平台。
- 平台化规则、复杂事件总线和高级分析能力后移到后续批次。
- 若引擎能力与主线闭环冲突，优先保证订单、库存、采购、物流、财务主链路正确。

## 13. 完成定义

完成本批次时，应满足以下标准：

1. `OMS → WMS → SCM → TMS → FMS` 至少两条主链路可通过集成测试验证。
2. 成本事件和利润结果可按订单追溯。
3. 关键非法状态有失败测试覆盖。
4. 所有改动继续遵守租户隔离、统一响应、路径规范和审计上下文约束。
5. 对应验收标准中的关键条目具备代码与测试证据。
